I2C

Protocol Overview

I2C uses two lines for communication Serial Data (SDA) and Clock (SCL). I2C is similar to SPI in that is synchronous, with the sampling being based on the SCL signal. One benefit of I2C is the ability to address certain chips on the bus within the I2C message frame. A brief overview of the message structure can be seen below:

Start Condition Address Frame R/W Bit ACK/NACK Data Frame ACK/NACK Data Frame 2 ACK/NACK Stop Bit
1 Bit (H->L Transition) 7 or 10 bits 1 bit 1 bit 8 bits 1 bit 8 bites 1 bit 1 bit

Similar to SPI, I2C separates devices into ‘controllers’ and peripherals’, due to there being only one data line (SDA) - only one device can communicate at a time.

In order to communicate properly wih an I2C device, the address of the device must be known. The address for an I2C device is often internally controlled and can be modified by asserting IO lines on the chip, this allows for multiple instances of that same chip to be on the same bus but share different addresses! The R/W bit (read / write) is used to determine the type of operation that will be performed on the I2C device. For example you may write to a register of an I2C based sensor in order to configure or initialize it, after that you would read the data from it.

See the example be low from the Sparkfun I2C tutorial for an additional explanation!

I2C For Reverse Engineers
  • I2C typically utilizes ‘open drain’ lines - so when the lines are not in use they are held high be a pullup resistor
  • i2cdetect can be used to detect what parameters are present on an i2c bus
    • i2cdetect -y BUS_NUM where BUS_NUM is 0/1 on the RPi depending on how you have it configured
  • Anyone can act as a I2C controller on the bus as long as you are not interrupting other communications, making in circuit analysis much easier than something like SPI where there may be contention for signal lines.
